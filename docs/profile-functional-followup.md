## 判断

### 导航与菜单卡顿

CPU 单独采样记录 18 次事件，最长约 616 ms。原始分析中，最长事件有约 382 ms 样本包含 `_UIHostingView.layoutSubviews()`，约 23 ms 包含自动化／无障碍调用。各类时间是包含关系，不能相加。整轮自动化开销较大，也不能解释每次布局卡顿。

当前证据不足以将某个业务函数认定为根因：采样中的主要 App 栈只有地址。CPU 重放所记录的 App UUID 为 `0FB9CCA5-D8BB-38C9-B441-A8FA4D54125C`，保留的 Release dSYM UUID 为 `57AE5E8E-35E0-3E3F-A708-646D3EE611A0`。二者不匹配，不能使用该 dSYM 的地址解析结果。

代码检查发现 ApplicationsView 在一次 body 求值中，列表、空态、图标加载任务标识和加载参数分别访问相同的筛选计算属性。现改为求值一次并复用。保留筛选规则、前 40 项图标加载范围及任务标识组成。此改动减少重复筛选，但没有证据证明它解决上述布局卡顿。

下一轮应保留与被测二进制 UUID 一致的 dSYM；先仅启用 Time Profiler，以人工操作重复应用菜单、标签切换和遥控中心开关，再按事件区间检查布局调用栈。另跑 XCTest 作为功能回归，不将其快照耗时当作人工交互性能。必须测量后才能报告改善幅度。

### 视频应用画面捕获失败

同一电视在视频应用返回 0 字节原生截图，在系统主页返回有效 PNG，且 App 主页预览与原生截图一致。这说明失败与当前电视画面场景有关；尚不能确定是内容保护还是固件行为。

现有 screenshot() 已验证 PNG 并保留 exec-out／pull 回退；不应将空文件视为成功。没有修改捕获权限、自动切换电视前台应用或尝试绕过内容保护。后续应在同一设备分别检查普通页面、视频页面和系统主页，并记录原生 screencap、screenrecord 的输出状态。只有 App 失败而原生捕获成功时，才有充分依据优先修复 App 捕获链路。

### Leaks 与内存

`libmalloc hasn't been initialized` 是本轮扫描工具失败，无法证明有或没有泄漏。RSS 从约 319 MiB 降到 302 MiB 也不能证明无泄漏。需在可正常扫描的环境重测，或通过多轮相同交互后存活对象与内存基线趋势进一步排查。当前不添加无依据的缓存清理。
